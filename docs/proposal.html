Five bugs surfaced only by running it, all fixed. On iOS: the status-bar Info.plist key was set the way that makes React Native throw on launch, and the result screen reported Saved −86% when the output legitimately grew (now Larger by 86%, with an explanation that HEVC beats JPEG on smooth images). On Android: a config plugin of mine overwrote Expo's generated debug manifest and broke every development build's Metro connection; File.toURI() emits file:/path with one slash, so a startsWith("file://") check silently missed and every conversion failed; and alpha was read from the decoder's target config rather than the source, so Android warned about flattening transparency on an opaque HEIC while iOS stayed quiet.

One honest platform difference remains, and it is not a defect: the same file converts to 96 KB on iOS and 32 KB on Android at the same quality setting, because ImageIO and Skia make different chroma-subsampling choices.

Two environment constraints worth knowing: React Native's build scripts break on a project path containing a space, so the checkout has to live somewhere without one; and Expo SDK 57 uses Swift syntax that Xcode 26.1.1 does not implement, which a self-disabling postinstall shim patches until Xcode catches up.

Decide these first

three conflicts in the brief · all resolved

Each of these is a place where two of your requirements cannot both be true. I have not picked a winner silently.

Blocks UI work

The attachment is a palette, not screenshots

Four swatches and the name Manrope give me colour and typeface. They do not give me the type scale, corner radii, spacing rhythm, elevation treatment, button and card anatomy, icon weight, or density — the things your brief names the screenshots as the source of truth for.

What I did: derived a complete token set from the palette, marked every assumption, and wrote no UI code. Send the real screens and I will reconcile before Phase 1 UI work begins.

Accessibility conflict

The palette's orange fails AA as a text colour

#D47E30 on the cream ground measures 2.92:1. It fails AA for body text (4.5:1) and fails even the 3:1 threshold for large text and UI components. White text on the orange is 3.08:1 — also a fail. The two browns are fine: 5.49:1 and 5.54:1.

Proposed adjustment, not a substitution: keep #D47E30 for what it is good at — large fills, progress bars, selected-card backgrounds, illustration — paired with #241708 ink at 5.68:1. For orange text, add #A85F1E, a darkened member of the same hue family, at 4.61:1. The palette's character is unchanged; text gains a legal place to live.

Store compliance conflict

"No data collected" is incompatible with the ad slot

§4 requires both privacy labels to read No data collected, and requires the claim to be true. §2.7 requires an AdMob banner. The Google Mobile Ads SDK reads the advertising identifier, device model, OS, locale and IP on every request — Play requires disclosing Device or other IDs, Apple requires Identifiers and Usage Data flagged as used for tracking, which triggers the ATT prompt. Sentry adds Diagnostics and Crash logs.

Resolved — zero third-party SDKs. No ad network, no crash SDK. Crash reports still arrive, free and without a line of code, through Xcode Organizer and Play Console Android Vitals: the user opts in once at the OS level and the data goes to Apple and Google, not to us, so it never touches our privacy label. Since an app whose whole workload is native image and PDF decoding crashes as native signals, that is the telemetry that matters — a JS-level SDK would see less of it. The IAP becomes a straight Support Development non-consumable at $2.99. A CI job greps the dependency tree for known ads, analytics and telemetry packages and fails the build if one appears, transitively included, so this cannot regress by accident.

One idea drives the whole design

the batch queue lives in native code

JavaScript submits one declarative job and then only observes. It never loops over files, never holds a buffer, never schedules work. That single decision is what makes four separate requirements achievable at the same time.

Why the queue cannot live in JavaScript
RequirementWhat breaks if JS drives it
Keep converting when backgrounded iOS suspends the JS runtime. A JS loop stops mid-batch. A native queue under beginBackgroundTask or an Android foreground service does not.
Share extension converts without launching the app An iOS share extension has roughly a 120 MB ceiling. Booting a React Native runtime inside it is slow and risks being killed. A plain Swift class in a shared framework runs zero JavaScript.
Cancel actually cancels Only the owner of the operation objects can abort work already in flight. From JS, "cancel" just stops enqueuing.
Peak memory under 400 MB across 300 images Per-file autorelease scoping and concurrency throttled by RAM class have to happen where the allocations happen.

ConverterCore is a product with its own test suite, not glue behind a bridge. The app, the iOS share extension and the Android share target are three peer clients of it. Progress events are coalesced natively to about 10 Hz before crossing the bridge — emitting per-file events at full speed for 500 files floods the JS thread and is the usual cause of stuttering progress bars in this category.

The finding worth your attention: the orange changes job between themes. On cream it cannot pass contrast, so it stays decorative. On the dark warm ground it reaches 6.09:1 and becomes the primary text accent, while the brown that carried text in light mode steps back to borders and surfaces. That preserves the relationships in your palette rather than naively inverting its values.

Type

Manrope for everything, per your brief. Your palette image sets its hex codes in a monospace face — I read that as intentional and propose carrying it into the product: all numeric and technical readouts — file sizes, pixel dimensions, compression percentages, format signatures — use the platform mono with tabular figures, as in the specimens above. It costs zero bytes (SF Mono and Roboto Mono are already on device) and it makes the before/after comparison on the result screen line up in columns instead of jittering. That screen is your stated shareable moment.

One licensing note: Manrope ships under SIL OFL-1.1, which is not on your permitted list as written. OFL is permissive and standard for bundled fonts, but the CI gate will fail on it unless the allowlist is extended deliberately — decision D5.

One source of truth, three languages

Decisions, as resolved

all five settled
D1

Screenshots, or a system derived from the palette?

Design to suit the palette. The token set above is now the source of truth. Send screenshots any time and I will reconcile against them.

D2

Ads and crash SDK, or a truthful "No data collected" filing?

Zero third-party SDKs. No ads, no Sentry. Platform-native crash reporting instead — free, no code, nothing on the privacy label. IAP becomes "Support Development", $2.99, restorable.

D3

Which native codecs to vendor?

All of them. libwebp, libjpeg-turbo, libavif + libaom, androidsvg. Every one is permissive and zero-cost; AAB per-ABI splits keep each install to roughly 6 MB of codecs. The full conversion matrix ships.

D4

Add #A85F1E as the text-safe orange?

Approved. In the palette as palette.amberInk, with a test that fails if a future palette change ever makes it redundant or makes it stop passing.

D5

Allow SIL OFL-1.1 in the licence gate?

Approved. Allowlisted for font assets so Manrope ships, with attribution in NOTICE and the in-app licences screen.

One environment blocker remains: no JDK is installed on this machine, so Android sources can be written and reviewed but not compiled locally until JDK 17 or 21 is available. Xcode 26.1.1 and Node 24.9.0 are fine, and iOS is unaffected.
